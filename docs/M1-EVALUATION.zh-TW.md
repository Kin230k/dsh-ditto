# M1 批量程式碼產規格驗收

建立日期：2026-09-15。這份驗收把不可妥協的確定性檢查，與模型文字品質分開。任何確定性檢查失敗時，不能用整體分數掩蓋。

## 確定性閘門

以下任一項失敗，整批直接不通過：

- 掃描結果中的每個 in-scope 模組恰好出現一次，排除項目與理由有計數。
- 不執行或 import 目標程式碼；不掃描 `node_modules`、輸出目錄、狀態目錄及明確排除目錄。
- 每個 evidence id 綁定真實相對路徑、有效行號範圍與內容 hash。
- 每個事實段落或清單項目至少引用一個已知 evidence id。
- 偽造 id、越界行號、來源 hash 變動、輸出碰撞、路徑跳脫、symlink escape 及既有目的檔都在寫入前拒絕。
- 核准樣本或批次指示修改後，revision 與 digest 必須改變。
- apply 只接受當前已審閱的 id、revision 與 digest；來源保持 byte-identical。
- 中斷後重跑不覆寫已完成輸出，逐項狀態與實際磁碟結果一致。
- fake generator 僅存在測試／合成 demo 路徑，介面清楚標示。

## 品質維度

模型品質以各維度獨立呈現，不先壓成單一分數：

| 維度 | 驗證方式 | M1 門檻 |
|---|---|---|
| 事實正確 | 人工對照程式碼及引用行 | ≥ 90% |
| 模組完整 | 對照掃描清單與輸出／待確認項目 | 100% 有交代 |
| 引用支持度 | 引用內容確實支持文字，不只路徑存在 | ≥ 90% |
| 格式一致 | 留出模組遵守核准樣本的章節與用詞 | ≥ 85% |
| 待確認誠實度 | 無證據資訊沒有被寫成確定事實 | 100% |
| 人工作業時間 | 與逐個交給 AI 的基線比較 | 中位數至少減少 50% |

初期品質樣本可以從 12 個合成模組起步，用於工程除錯；宣稱產品品質前需擴充到至少 20 組不同結構的 repository fixtures，並加入真實使用者提供且允許測試的專案。

## 必測案例

- Express route、service、資料型別與一般工具模組，確保樣本不是只取排序最前面三份。
- 僅有 export、沒有註解的模組。
- 動態 route 或框架無法確定的行為，應進入待確認。
- 超過大小限制、二進位、generated、測試、build 目錄，應明確排除。
- 兩個來源推導出相同輸出名稱。
- 模型提交不存在的 evidence id。
- sample edit 改變章節順序或術語後，test generator 的留出模組跟著改變。
- apply 途中失敗，再次執行只處理尚未完成項目。

## 基線比較

同一批 12–20 個模組分別用兩種方式完成：

1. 逐個把檔案交給 AI、重複說明格式、人工收集輸出。
2. Ditto 只校準三份樣本，再處理全批。

記錄完成時間、人工互動次數、漏模組數、無證據主張數、格式修正次數與模型 token。只有 Ditto 在完整度不下降的前提下顯著減少操作，才算核心用途成立。
