## User journey

1. Pick a source folder and enter what a consistent output should look like.
2. Inspect 3 representative original → proposed names. Edit the proposed names before committing.
3. Review the full batch with missing/conflicting items clearly visible.
4. Create organized copies in a new output directory. Originals stay intact.
5. Inspect per-file results and save a versioned recipe for next time.

M0 demonstrates deterministic filename recipes plus reviewed per-file overrides; AI semantic inference is explicitly not claimed. Native DSH agent may provide proposed names using normal DSH model reasoning; code validates/applies proposals. One approved sample does not magically learn a transformation in M0.

## Shared surface

Core expose a straightforward JSON-serializable Plan, Recipe, PlanItem and ApplyResult, plus createPlan, revisePlan, applyPlan, loadPlan, saveRecipe/loadRecipe or equivalents. Send concrete exported signatures to UI worker early. Keep server-independent pure recipe/name planning reusable in browser where practical. Node filesystem side creates SHA-256 source snapshots and safe destination metadata.

UI should be a self-contained interactive local artifact, generated by exported renderWorkbench(plan) returning HTML, with no CDN. A small loopback-only preview server may be implemented by the core worker to back real apply/revise/save operations; keep it strictly within an explicit launch workspace, with request size limits, CSRF token and Origin checks, no arbitrary-root API changes. Alternatively a browser file-upload + download flow can demonstrate real copies but must state its limitations. Agree one integration approach with core; do not ship a fake apply button.

Suggested local server API: GET /api/plan -> current plan; POST /api/revise {revision, edits:[{id,destination}]} -> new plan; POST /api/apply {revision,digest} -> actual result; POST /api/recipe {name} -> persisted recipe; GET /api/recipe -> saved recipe summaries. Server injects nonce in rendered HTML for mutation headers. No generic filesystem or shell API. All operations stay inside launch source/output roots. CLI demo creates synthetic fixtures inside this repository's ignored .local directory, never touches user's real documents.

Native DSH: expose preview/revise/apply/status/recipe through minimal public tools. Apply requires exact plan ID + reviewed digest (an integrity check, not proof of human approval); tool guidance requires user's batch approval in normal use. This session's synthetic demos are authorized. Package bundle/profile composition and a keyless real-host smoke are required to call it integrated. Do not recreate full presets from rc.5.

## Release scope

Pass M0 means functional sample preview/edit/apply and persisted recipe, real copied outputs, non-overwrite/path/staleness tests, and clear DSH integration evidence. It does not mean market validation, full semantic learning, support for every document format, production deployment or proof of originality.
